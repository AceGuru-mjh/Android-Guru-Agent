# v1.4.8 更新体系修复（签名漂移 / SD 卡 / 增量 APK 持久化）

> 本次修复针对用户反馈的三个增量更新问题，根因定位与修复方案记录于此，
> 供后续维护与故障复盘参考。

## 问题清单

| # | 现象 | 根因 |
|---|---|---|
| 1 | 增量安装覆盖时报**签名不一致** | `app/build.gradle.kts` release 用 `signingConfigs.getByName("debug")` —— debug.keystore 是机器本地的，CI runner 与开发者本机必然不同；VCDIFF 合成的 APK 字节级保留源 APK 签名块，但远端新版是 CI debug key 签的 → `INSTALL_FAILED_UPDATE_INCOMPATIBLE` |
| 2 | 补丁合成的 APK 装完后在**关于页消失** | `AboutUpdatePanel.kt` 在 UpToDate 时清掉所有 `ApexAgent-v*-patched.apk`；有更新时清非目标版本合成包 → 用户装完补丁后版本追平判 UpToDate → 合成包被自动清理 |
| 3 | 部分最新 APK 安装提示**未找到 SD 储存卡** | `UpdateDownloader.installApk` 用 `Intent.ACTION_VIEW` + FileProvider `external-path` 映射 Downloads 目录；MIUI/EMUI 部分版本的系统安装器进程无法解析 external storage 的 `content://` URI |

## 修复方案

### 1. 签名漂移根因修复（固定入库 keystore）

**新增**：
- `keystore/apex-release.jks` —— PKCS12 格式，凭据 `name=meng411722 / key=meng411722`，50 年有效期
- `keystore/.gitignore` —— 排除 `.bak` 备份，保留 `.jks` 入库
- `scripts/generate_release_keystore.sh` —— 幂等生成脚本（已存在且指纹匹配则跳过）

**修改 `app/build.gradle.kts`**：
- 新增 `signingConfigs.release` 块，读 `keystore/apex-release.jks`
- `buildTypes.release`：`signingConfig` 从 `debug` 改为 `release`
- `buildTypes.debug`：默认也用 `release` 签名（本地构建可覆盖装 CI 发布版）
- `enableV1Signing/v2/v3` 全开（v2 是 Android 7+ 覆盖安装首选，v1 兼容旧机）

**逃生门**：
- Gradle 属性：`-PapexKeystoreFile` / `-PapexKeystorePassword` / `-PapexKeyAlias` / `-PapexKeyPassword`
- 环境变量：`APEX_KEYSTORE_FILE` / `APEX_KEYSTORE_PASSWORD` / `APEX_KEY_ALIAS` / `APEX_KEY_PASSWORD`
- debug 构建回退纯调试签名：`-PapexDebugSign=true`

**签名证书 SHA-256 指纹**（注入 `version.json.signingCertSha256`，客户端签名预检基准）：
```
bcb9dfdd9b2e197c90ab19fb80fa68fcbf9a9f180702d51b268069538303c913
```

**为什么入库 keystore**：
个人项目经 GitHub Releases 侧载分发（非 Play Store），入库 keystore 是开源
Android 应用的标准做法（Termux / F-Droid 同款）。CI 与本地构建共用同一份 →
签名指纹恒定 → 增量合成 APK 与已装 APK 签名一致 → 覆盖安装无冲突。

**升级注意**：
已装旧版（debug 签名）的用户首次升级到新签名版时，由于签名密钥切换，
**必须卸载重装一次**（一次性代价）。之后所有版本（CI / 本地 / 增量合成）
签名一致，覆盖安装永久无冲突。

### 2. 「未找到 SD 储存卡」修复（cache-path 授权）

**修改 `UpdateDownloader.installApk`**：
1. **优选路径**：先把 APK 复制到 `context.cacheDir/install_apk/`，用
   FileProvider 的 `cache-path` 映射授权（`xml/file_paths.xml` 已有
   `<cache-path name="cache" path="." />` 配置）。cache 目录是 app 私有，
   安装器进程持 granted URI permission 必能读 → 所有 ROM 兼容。
2. **兜底路径**：cache 复制失败（磁盘满 / 权限异常）时回退原 `external-path`
   方式（部分 ROM 仍可能报 SD 卡错误，但比直接放弃强）。
3. intent 加 `FLAG_ACTIVITY_RESET_TASK_IF_NEEDED`（MIUI 某些版本需要）。

日志记录来源（`cache-copy` / `external`）便于诊断。

### 3. 增量 APK 持久化（关于页常驻「本地更新包」区）

**根因**：三处自动清理逻辑把用户辛苦合成的 `-patched.apk` 清掉：
- `AboutUpdatePanel.kt` UpToDate 时清所有 `ApexAgent-v*-patched.apk`
- `AboutUpdatePanel.kt` 有更新时清非目标版本合成包
- `PatchUpdateEngine.cleanStaleIntermediates` 开工时清所有 `-patched.apk`

**修法**：三处都改为**只删 `chain-step` 中间件 + 链外 `.vcdiff`**，保留所有
`-patched.apk`（用户辛苦合成的，即使版本 != 远端最新也保留）。

**新增「本地更新包」常驻区**（关于页任何状态都展示）：
- `AboutUpdatePanel.kt`：`localApks` state + `scanLocalApks`（进入页面即扫描，
  每 2 秒轮询刷新；流水线下载/合成时清单实时更新）
- `AboutUpdateWidgets.kt`：`LocalApkInventorySection` 组件 —— 每条显示
  版本号 / 种类徽章（增量合成 / 全量·arm64 / 全量·universal）/ 体积 / 文件名 +
  安装/删除按钮，高度上限 320dp 可滚动
- 指纹不符的坏文件：仅当文件名匹配远端目标版本时才删（坏文件留着也是坏的），
  版本不匹配（用户已装新版但旧合成包还在）则保留

**模型**：
- `LocalApkKind` enum：`PATCHED` / `FULL_ARM64` / `FULL_UNIVERSAL` / `UNKNOWN`
- `LocalApkEntry` data class：`file` / `sizeBytes` / `kind` / `versionLabel` / `lastModified`
- `extractVersionLabel(fileName)`：从 `ApexAgent-v1.4.8-patched.apk` 解析出 `1.4.8`

**字符串资源**（values + values-zh，8 条）：
- `about_update_local_inventory_title` / `hint`
- `about_update_local_kind_patched` / `full_arm64` / `full_universal` / `unknown`
- `about_update_local_install` / `delete`

## 与既有通道的关系（修复后）

| 通道 | 适用 | 安装 | 签名冲突 |
|---|---|---|---|
| **热更**（v1.4.7） | data-only 版本 | 零安装，即时生效 | 不存在（不碰 APK） |
| **增量**（vcdiff） | 官方渠道 + 签名一致 | 合成后系统安装器 | v1.4.8 起签名固定 → 无冲突 |
| **全量** | 兜底 | 系统安装器 | 同上 |

**关于页常驻「本地更新包」区**：无论更新检查状态如何（Available / UpToDate /
Failed），用户都能随时找到 `Download/ApexAgent/` 下已下载/合成的 APK 一键
安装或删除，无需 MT 管理器。
